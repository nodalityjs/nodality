# v1.3.14 — draft

> Draft only. Edit freely and paste into the GitHub release; nothing here is published.

## `nav` is built from what the page says

A `nav` collapses its links behind a menu button below a breakpoint, which is
what a site's navigation needs on a phone. Until now it ignored almost
everything a page gave it. The mapper read `items` and `id`; the rest was a
hardcoded demo — brand "Company", background `#ecf0f1`, a blue menu button,
1rem corners — plus a "More" dropdown of placeholder links whose icons were
loaded from a third-party CDN on every page view. The schema advertised ~170
parameters for the type and `validate_nodes` accepted them all, so a page could
set `brand`, `background` and `radius`, pass validation, and get the demo.

A nav that declares `items` is now built from its own options:

```js
{ type: "nav", id: "nav",
  brand: "Acme",                       // or an element spec: { type: "p", text, keySet, … }
  items: [{ title: "Work", link: "#work" }, { title: "Contact", link: "#contact" }],
  breakpoint: 768,                     // the full bar from here up; default 1200px
  font: "Inter", color: "#111", hover: { color: "#b83a0b" },
  background: "rgba(255, 255, 255, 0.8)", radius: "14px", mar: [{ a: 0 }], pad: [{ tb: 12, lr: 24 }],
  keySet: [{ key: "backdropFilter", value: "blur(20px)" }],
  menuLabel: "Menu" }
```

- Each of those is described in `get_schema nav`, with its shape.
- No demo dropdown and no third-party request unless `dropdown` is asked for.
- Where a page says nothing, the defaults are the ones the nav always used.
- A nav declared **without** `items` is the demo, unchanged.

## The menu button is accessible, and following a link closes the menu

- The button is a real `type="button"` with an accessible name (`menuLabel`,
  default "Menu") and `aria-expanded` that follows the menu; it names the menu
  it controls. It used to be announced as "☰".
- Following a link closes the menu. On a one-page site the links are anchors,
  and a menu left open covered the section it had just scrolled to.

## Prerendered pages carry their nav

The prerenderer emulates a phone and answers media queries against it, but it
answered every *range* query — `(min-width: 0px) and (max-width: 1199px)` — with
false, on the belief that Nodality never emits one. The Switcher behind every
nav does, so no view matched and every nav reached crawlers and no-JS readers as
an empty box. Ranges now resolve. Where there is no `matchMedia` at all (a bare
jsdom), a Switcher shows its widest view rather than nothing.

## Fixes

- `MobileBar.toCode()` emitted a fixed handful of options, and Des renders by
  running that code — so `hamburgerColour`, and anything else outside the list,
  never reached a page. It now emits every option the bar reads, and no longer
  throws on a bar without a brand.
- `MobileBar` no longer logs "Appending brand:" to the console on every load.
- `DesktopBar` accepts `color` and `keySet`.

## The conformance probe could not see a nav

The test that checks every advertised parameter changes the rendered DOM
answered every media query with false, so no Switcher view ever rendered and
the whole `nav` type read as inert — its baseline recorded the probe's
blindness as the component's. It now answers width queries against a real
width and probes at 390px and 1440px. Six `nav` entries left the known-inert
baseline because they now work.
